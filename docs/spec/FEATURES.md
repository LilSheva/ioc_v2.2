# FEATURES: Спецификация функциональных возможностей парсера

Этот документ детально описывает алгоритмы извлечения и нормализации индикаторов компрометации (IOC) из документов.

---

## 1. Режимы парсинга документов

Парсер поддерживает два специализированных режима обработки документов в зависимости от их источника:

### 1.1. Режим ФСТЭК (fstek)
Ориентирован на бюллетени ФСТЭК России. Характеризуется наличием списков хэш-сумм или сетевых адресов, разделенных точкой с запятой.
* **Предварительный разбор списков (Pre-parsing)**:
  - Перед началом работы стандартных регулярных выражений парсер ищет блоки текста под заголовками списков (например, `спискам:`, `(md5):`, `(sha256):` и т.д.) до ближайшей точки `.`.
  - Найденная строка разбивается по символу `;`. Каждый элемент очищается от пробелов и заносится в результаты как хэш или сетевой индикатор.
  - Извлеченный текст списка заменяется пробелами в рабочем буфере текста документа, чтобы стандартный регулярный парсер не продублировал эти значения.
* **Последующий общий поиск**:
  - После разбора списков выполняется стандартный RegExp-поиск по всему оставшемуся тексту бюллетеня (для извлечения единичных IP, доменов или email, упомянутых в тексте вне списков).

### 1.2. Режим Госсопка (gossopka)
Ориентирован на бюллетени НКЦКИ. Документы часто содержат последовательные текстовые абзацы, разделенные визуальными горизонтальными линиями, но не оформленные в таблицы.
* **Сегментация по границам абзацев (Borders)**:
  - Парсер группирует абзацы в изолированные логические секции.
  - Разделителем секций выступает абзац, у которого в свойствах XML (`w:pPr`) обнаружен элемент границы абзаца (`w:pBdr/w:top` или `w:pBdr/w:bottom`).
* **Последовательное определение статусов (Sequential Statusing)**:
  - Внутри каждой секции может находиться несколько индикаторов и несколько ключевых слов. Статус для каждого индикатора определяется локально.
  - Индикаторы сортируются по их позиции в тексте секции.
  - Для каждого индикатора анализируется предшествующий ему текст (начиная от конца предыдущего индикатора или начала секции). Ищутся ключевые слова:
    - `unblock` (разблокировка): `разблокиров`, `разблокира`, `легитимный`
    - `block` (блокировка): `для поиска и блокировки`, `блокиров`, `блокировка`
    - `search` (поиск): `для поиска`
  - Если ключевые слова в предшествующем тексте отсутствуют, анализируется текст после индикатора (до следующего индикатора или конца секции).
  - Если ключевые слова не найдены ни до, ни после, индикатору присваивается статус по умолчанию — `block`.

## 2. Алгоритмы очистки и нормализации данных

### 2.1. Сшивание URI (Stitching)
- Если URI в документе был разбит переносом строки, парсер сшивает его на этапе подготовки текста, удаляя перенос строки и любые окружающие пробелы. Это позволяет извлекать единый корректный URI.

### 2.2. Защита доменов и URI с опечатками (_smart_clean_uri)
- Маскирующие символы (`[.]`, `[:]`, `hxxp`) удаляются перед валидацией.
- Для извлечения домена используется встроенный `urllib.parse.urlparse`. 
- В случае сбоя парсинга (например, при наличии тройных слэшей `///` или некорректного формата), применяется резервное регулярное выражение `://([^/:]+)` для надежного извлечения имени хоста.
- Важно: В Excel-отчетах в колонке "Indicator" пишется сырой найденный текст, а в колонке "IOC" (очищенный индикатор) — очищенный домен/URI без префиксов схемы `http://` / `https://` (для совместимости с SIEM/сетевыми экранами). При этом во внутренних структурах префикс сохраняется для обратной совместимости с тестами.

### 2.3. Сохранение квадратных скобок в именах файлов
- Для сетевых индикаторов квадратные скобки (демаскирование `[.]`) удаляются.
- Для файлов квадратные скобки, содержащие описание шаблонов (например, `[множество пробелов]`), должны сохраняться (например, `Scan_[множество пробелов].exe`), так как они указывают на нелитеральный характер строки. Внутренний метод `clean_ioc` удаляет скобки только в случае, если тип индикатора не равен `File`.
