# Нюансы реализации: Ядро (Core Package)

Этот документ описывает внутреннее устройство и ключевые алгоритмы ядра бизнес-логики, расположенного в директории [ioc_analyzer/core/](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/).

---

## 1. Доменные модели ([models.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/models.py))

Ядро оперирует тремя ключевыми структурами (декорированными как `@dataclasses.dataclass`):
* **`IOC`**: Представляет отдельный индикатор компрометации. Содержит поля:
  - `value`: Очищенное значение (например, `192.168.1.1`).
  - `raw_value`: Исходная строка из текста (например, `192[.]168.1.1`).
  - `ioc_type`: Тип индикатора (IP, DNS, URI, File, MD5 и т.д.).
  - `status`: Действие (block, search, unblock).
  - `context`: Предложение или абзац из документа, в котором найден индикатор.
* **`EmailRecord`**: Метаданные электронного письма из Exchange. Содержит `mail_id` (compound ID в виде `id:changekey`), `sender`, `subject`, `date` и пути к сохраненным вложениям.
* **`ReportData`**: Объединенные результаты парсинга бюллетеня. Содержит списки извлеченных IOC, номера бюллетеней, дату, организацию и списки уязвимостей (`bdu_list`).
* **`AppSettings`**: Настройки регулярных выражений и системных параметров.

## 2. Логика работы парсеров ([core/parser/](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/parser/))

Парсинг разделен на модули для поддержки ограничения в 250 строк.

### 2.1. Базовый парсер ([base_parser.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/parser/base_parser.py))
* Использует скомпилированные регулярные выражения из конфигурации.
* Выполняет проход RegExp по тексту. Для каждого совпадения определяет контекст (предложение вокруг позиции совпадения).
* Дедуплицирует индикаторы по уникальному значению `value`.

### 2.2. Модуль очистки ([cleaner.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/parser/cleaner.py))
* **Сшивание строк (Stitching)**: Предварительно ищет разорванные переносимыми строками URI и склеивает их, удаляя пробелы и спецсимволы разрыва.
* **Деобфускация (`_smart_clean_uri`)**:
  - Заменяет `[.]` на `.`, `[:]` на `:`, `hxxp` на `http`, `[at]` на `@`.
  - Извлекает домен/хост с помощью `urllib.parse.urlparse`.
  - При возникновении ошибок разбора URL (например, из-за опечаток или тройного слеша `///`) применяется резервное регулярное выражение `://([^/:]+)` для надежного вырезания домена.
* **Сохранение квадратных скобок в именах файлов**:
  - Для доменов и IP квадратные скобки удаляются полностью.
  - Для файлов квадратные скобки часто содержат шаблоны (например, `[множество пробелов]` или `[0-9]`). Метод `clean_ioc` сохраняет квадратные скобки, если тип индикатора равен `File`.

### 2.3. Специфика ФСТЭК ([fstek_parser.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/parser/fstek_parser.py))
* **Pre-parsing списков**:
  - Находит заголовки списков (например, `хэш-сумм файлов:`, `ip-адресов:`) и парсит весь блок текста до первой точки `.`.
  - Текст списка разбивается по `;`, очищается от пробелов.
  - Чтобы стандартный RegExp-парсер не обрабатывал эту область повторно, найденный блок в рабочем буфере заменяется пробелами аналогичной длины.
* После обработки списков запускается стандартный проход регулярных выражений по оставшемуся тексту бюллетеня.

### 2.4. Специфика ГосСОПКА ([gossopka_parser.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/parser/gossopka_parser.py))
* **Сегментация по границам**: Документ делится на логические блоки на основе горизонтальных линий (переданных из адаптера docx через XML-свойства абзацев).
* **Локальное определение статусов (Sequential Statusing)**:
  - Внутри блока индикаторы сортируются по позиции.
  - Для каждого индикатора сначала анализируется предшествующий текст (от конца предыдущего индикатора до текущего). Ищутся триггеры действий (`block`, `unblock`, `search`).
  - Если триггеры не найдены, анализируется последующий текст (до начала следующего индикатора).
  - Если триггер не определен — присваивается статус `block` по умолчанию.

## 3. Построитель запросов ([query_builder.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/query_builder.py))

* Преобразует списки однотипных индикаторов (например, IP или доменов) в строковые фильтры для MaxPatrol 10 и PT NAD.
* Форматирует вывод согласно шаблону: `field in ["val1", "val2"]`.
* **Разбивка на чанки**: Если количество индикаторов превышает заданный лимит (например, 100 элементов), список автоматически бьется на несколько запросов, объединяемых через `OR` (для MP10) или `||` (для NAD).
* Этот модуль используется как для генерации Excel-файла фильтров, так и для отображения поисковых строк на вкладке GUI "Результаты запросов".

## 4. Оркестратор бизнес-логики ([service.py](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/ioc_analyzer/core/service.py))

* Класс `AppService` управляет общим жизненным циклом.
* Не имеет собственного состояния (state-free): все данные передаются через аргументы или возвращаются из методов.
* Обрабатывает как локальные файлы (`parse_local_file`), так и входящую почту в цикле демона (`process_pending_bulletins`).
