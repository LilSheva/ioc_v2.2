# Общие правила разработки и кодирования (General Rules)

Этот документ содержит требования к стилю кодирования, документированию, тестированию и качеству программного кода в проекте **IOC-Analyzer**. Все ИИ-агенты и разработчики обязаны строго соблюдать эти правила при написании кода.

---

## 1. Лимиты на размер файлов (MAX_FILE_LINES = 250)

Для предотвращения создания нечитаемых монолитных скриптов вводится строгое ограничение на размер исходных файлов.

### 1.1. Правило 250 строк:
Максимальный размер любого Python-файла (`.py`) составляет **250 строк кода**.
* **Что учитывается:** Учитываются только непосредственно строки исполняемого кода. Пустые строки и строки комментариев (включая многострочные docstrings) в этот лимит **не входят**.
* **Как проверять:** Используйте статический анализатор или проверяйте количество строк перед сохранением.

### 1.2. Стратегия разделения (Splitting Strategy):
Если при добавлении функционала файл превышает лимит:
1. Выделите логическую группу функций или классов в новый файл (модуль) в той же директории.
2. Дайте новому файлу понятное имя (например, если разделяется GUI вкладка `settings_tab.py`, вспомогательные виджеты выносятся в `settings_widgets.py`).
3. Импортируйте нужные классы/функции в исходный файл.
4. Убедитесь, что циклические импорты отсутствуют.

## 2. Статическая типизация (Type Hinting)

Весь код должен быть строго типизирован. Использование динамической типизации без аннотаций запрещено.

* **Аргументы и возвращаемые значения:** Каждая функция и метод должны декларировать типы входных параметров и тип возвращаемого значения.
* **Сложные типы:** Используйте встроенные типы (`list[...]`, `dict[...]`, `tuple[...]`, `set[...]`) для Python 3.9+ или модуль `typing` (`Any`, `Optional`, `Callable`, `Union`) для обеспечения гибкости.
* **Пример:**
  ```python
  def parse_bulletin(self, file_path: str, mode: str) -> Optional[ReportData]:
      ...
  ```

## 3. Документирование (Google Style Docstrings)

Каждая публичная сущность (класс, метод, функция, модуль) должна быть задокументирована в соответствии с **Google Python Style Guide**.

* **Язык документации:** Допускается русский или английский язык.
* **Структура docstring:**
  - Краткое описание назначения.
  - Секция `Args` с описанием типов и роли аргументов.
  - Секция `Returns` с описанием возвращаемого значения.
  - Секция `Raises` (если метод явно генерирует исключения).
* **Пример:**
  ```python
  def calculate_hash(data: bytes, hash_type: str = "sha256") -> str:
      """
      Вычисляет криптографический хеш от переданного массива байт.
  
      Args:
          data: Входные байты для хеширования.
          hash_type: Алгоритм хеширования (поддерживаются "sha256", "sha1", "md5").
  
      Returns:
          Строковое представление хеша в шестнадцатеричном формате.
  
      Raises:
          ValueError: Если передан неподдерживаемый алгоритм хеширования.
      """
  ```

## 4. Логирование и обработка ошибок

### 4.1. Запрет на `print()`
Использование встроенной функции `print()` в исходном коде проекта **запрещено** (за исключением тестов или скриптов сборки, если необходимо).
* Для вывода отладочной и рабочей информации используйте стандартный модуль `logging`:
  ```python
  import logging
  logger = logging.getLogger(__name__)
  
  logger.info("Процесс парсинга успешно начат для файла: %s", file_path)
  logger.error("Ошибка при чтении почты Exchange: %s", str(err), exc_info=True)
  ```

### 4.2. Обработка исключений
* **Никаких пустых блоков catch:** Код вида `try: ... except: pass` категорически **запрещен**.
* **Специфичные исключения:** Всегда перехватывайте конкретные типы ошибок (например, `FileNotFoundError`, `requests.RequestException`).
* **Логирование ошибок:** При перехвате системных ошибок обязательно логируйте трассировку стека (`exc_info=True`) или сохраняйте сообщение об ошибке в логи.

## 5. Кодировка файлов

Все файлы проекта должны сохраняться в кодировке **UTF-8 без BOM**. При открытии файлов в коде (например, чтение JSON-конфигурации или текстовых файлов) всегда явно указывайте параметр `encoding="utf-8"`:
```python
with open("config.json", "r", encoding="utf-8") as f:
    config = json.load(f)
```

При добавлении новых возможностей или изменении логики парсинга вы обязаны добавлять соответствующие юнит-тесты.
* **Фреймворк:** Используется `pytest`.
* **Расположение:** Все тесты находятся в папке [tests/](file:///d:/Рабочая Папка/ioc_parser_srv/1_project/tests/).
* **Именование:** Тестовые модули должны иметь префикс `test_`, тестовые функции — также `test_`.
* **Запуск тестов:** `python -m pytest 1_project/tests/`.
