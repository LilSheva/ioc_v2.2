# Legacy vs Refactor Audit (`branch_feature_server_mode` -> `1_project`)

## Executive summary

Рефакторинг в `1_project` в целом успешен: проект перешел с монолитной связки `controller/model/view` на явную слоистую схему `core + ports + adapters`, а часть критичных legacy-проблем (сломанный server mode, `NameError` в нейминге отчета, отсутствие `Registry` в извлечении) устранена.

При этом обнаружены два класса остаточных проблем:

1. **Архитектурно-функциональные разрывы при переносе** (или недоперенос): несогласованность API-комментариев в daemon-пути, неиспользуемые/мертвые настройки, частичная потеря поведения legacy.
2. **Нарушения собственных правил `1_project`** по `AGENTS.md` и `docs/rules.md`: лимит 250 строк, запрет `print`, запрет `except: pass`/bare `except`, расхождение документации и фактического поведения.

Итог: рефакторинг дал сильную базу, но для действительно «production/диплом-ready» состояния нужен короткий стабилизационный цикл по приоритетам P0-P2 (ниже).

## Feature parity

### Что сохранено или улучшено

- **Архитектура и декомпозиция:** вместо одного крупного `AppController` из legacy введены `AppService`, порты и адаптеры (`document`, `mail`, `export`, `ip_block`, `gui`).
- **Режимы парсинга:** ФСТЭК/ГосСОПКА сохранены; в `1_project` добавлен более устойчивый детект режима (`mode_detect`) и поддержка `auto`.
- **Парсинг ГосСОПКА:** реализована сегментация по границам абзацев и последовательное определение статусов внутри секций.
- **Набор IOC:** поддержка всех ключевых типов сохранена, включая `Registry` (в legacy-ветке это было проблемой).
- **Экспорт:** сохраняются XLSX-отчеты IOC, фильтры, отчет уязвимостей, CSV-шаблоны.
- **API блокировки IP:** сохранены per-IP статусы ответа API и UX-колонка статуса отправки в GUI.
- **Daemon:** вместо одноразового `--server` цикла legacy введен непрерывный daemon с интервалом, EWS-интеграцией и режимом `-tst` для S/MIME.

### Что работает частично (паритет неполный)

- **Редактируемость regex через GUI:** в документации заявлена, в коде фактически отсутствует (regex не редактируются в settings-вкладке).
- **Контракт «regex из конфигурации»:** в парсере часть типов по-прежнему идет по захардкоженным паттернам (Email/URI/DNS/File), а не по `config.json`.
- **GUI responsiveness:** тяжелые операции запускаются синхронно; legacy-риск «заморозки» UI концептуально остался.

## Lost/deprecated

### Осознанно deprecated (ожидаемо)

- **`token.key` + XOR/Base64 схема** из старого ТЗ (`upd.txt`) удалена/не перенесена в `1_project` (и это корректно по поздним аудитам и договоренностям).
- **Outlook COM-пайплайн** (`win32com`-ориентированный server cycle legacy) заменен на EWS (`exchangelib`).

### Вероятно потеряно при переносе (нужно решение)

- **Архивация `.msg` письма**: в legacy-пайплайне сохранялся `.msg`; в `1_project` сохраняются вложения + `body.txt`, но не `.msg`.
- **`preserve_existing_files` как реальная функция:** флаг есть в конфиге и моделях, но по коду фактически не влияет на путь скачивания/копирования вложений.
- **Часть старой совместимости хранения state:** legacy-модель с `ioc_parser_settings.json` + миграцией из `config.txt` не перенесена как миграционный слой в `1_project` (сделан новый `config.json`-центричный подход).

### Изменено в формате результатов

- **Выходной BDU-артефакт:** в старых инструкциях встречался `.txt`, в `1_project` это XLSX-отчет уязвимостей.

## Thin spots & risks

### Критичные нарушения собственных правил проекта (`AGENTS.md`, `docs/rules.md`)

- **Лимит 250 строк нарушен:**
  - `run_gui.py` (~407 строк),
  - `ioc_analyzer/core/service.py` (~263 строки).
- **Запрет на `print()` в прод-коде нарушен:**
  - `ioc_analyzer/adapters/export/excel_report.py`,
  - `ioc_analyzer/adapters/export/excel_filters.py`,
  - `ioc_analyzer/adapters/export/csv_report.py`.
- **Запрет bare `except`/`except: pass` нарушен в нескольких модулях:**
  - `core/parser/cleaner.py`,
  - `core/query_builder.py`,
  - `core/config_manager.py`,
  - части mail/gui/export-слоя.

### Логические/функциональные риски

- **Regex-контракт и UI не совпадают:**
  - settings-tab не дает редактировать regex,
  - парсер использует hardcoded regex для части IOC.
  - Следствие: оператор думает, что правит regex в конфиге/GUI, но поведение не меняется.
- **Потеря контекста при дедупликации:**
  - дедуп по `clean_value` в сервисе может схлопывать разные статусы/источники одного IOC.
- **Несогласованность комментариев API (daemon vs GUI):**
  - daemon-path формирует `ip_comments` из `context/source_file`,
  - GUI-path формирует комментарии из bulletin/filename-логики.
  - Следствие: разные семантики комментария для одного и того же API.
- **`preserve_existing_files` фактически не работает как опция:**
  - параметр присутствует, но его поведение не прослеживается в критическом пути обработки вложений.
- **Перезапись вложений с одинаковыми именами в одном письме (риск коллизий):**
  - в EWS-адаптере базовый save-path не обеспечивает уникализацию имени для обычных FileAttachment.
- **Транспорт API по умолчанию HTTP + отсутствие chunking:**
  - риск утечки ключа/данных в сети и таймаутов/перегрузки при больших списках IP.
- **Документация и код расходятся в ряде обещаний:**
  - safe-write retries в документации описаны шире, чем реально реализованы в коде;
  - «редактирование regex в GUI» заявлено, но фактически отсутствует.

## Recommendations (приоритеты)

### P0 (сделать первым)

1. Привести код в соответствие `docs/rules.md`:
   - разбить `run_gui.py` и `core/service.py` до лимита,
   - убрать `print` из прод-модулей экспорта,
   - заменить bare `except` на специфичные исключения + логирование.
2. Зафиксировать единый regex-контракт:
   - либо полностью конфигурируемый regex для всех IOC,
   - либо явно задокументировать hardcoded-типы и убрать иллюзию редактируемости в GUI.
3. Исправить дедуп-логику IOC для сохранения статусов/источников (минимум ключ `clean_value + status + source`).

### P1

1. Унифицировать API-комментарии между daemon и GUI.
2. Реализовать operational-надежность из старого плана:
   - retry-журнал отправки IP,
   - карантин/обработка проблемных писем,
   - политика повторных попыток.
3. Починить/удалить мертвую настройку `preserve_existing_files`; добавить уникализацию вложений.

### P2

1. Перевести IP-валидацию на `ipaddress.ip_address` (IPv4/IPv6, без ложноположительных `inet_aton`-кейсов).
2. Добавить API chunking + ограничение размера батча.
3. Ввести явный режим безопасности API (предупреждение/блок для `http://` в прод-конфиге).
4. Синхронизировать docs с реализацией (чтобы спецификация была защитимой и проверяемой).

### P3

1. Расширить автотесты на граничные operational-сценарии:
   - коллизии вложений,
   - дедуп со смешанными статусами,
   - retry/карантин и поведение daemon при частичных сбоях.
2. Добавить в релизный чеклист обязательный ручной GUI smoke (API-статусы, отображение unblock, сохранение отчетов).
